# GH05T3 WSL Bridge

The WSL bridge lets Linux-native processes (Python 3.12, lightweight inference) run alongside the Windows stack. WSL connects back to Ollama and the rest of the GH05T3 services via the Windows host IP.

**Key fact**: WSL services are OPTIONAL. All 291 tests pass without WSL. The 6 WSL tests auto-skip unless `WSL_SERVICES_UP=1` is set.

---

## Quick Start

```powershell
# From Windows PowerShell — launch WSL services
native\windows\START_WSL.bat

# Or manually from WSL:
wsl bash ~/gh05t3-wsl/wsl_start.sh
```

```bash
# From inside WSL:
source ~/.gh05t3-wsl.env
cd ~/gh05t3-wsl
./wsl_start.sh
```

## One-Time Setup

Only run this if the `~/gh05t3-wsl/` venv doesn't exist yet:

```bash
# Inside WSL
bash /mnt/c/Users/leer4/GH05T3/scripts/wsl_setup.sh
```

What it does:
1. Creates `~/gh05t3-wsl/` venv (Python 3.12)
2. Installs `backend/requirements-wsl.txt` into the venv
3. Copies `wsl_start.sh` and `wsl_stop.sh` to `~/gh05t3-wsl/`
4. Creates `~/.gh05t3-wsl.env` with auto-detected `WIN_HOST_IP`

## ~/.gh05t3-wsl.env

```bash
# Auto-generated by wsl_setup.sh — edit if WIN_HOST_IP changes
export WIN_HOST_IP=172.30.96.1
export OLLAMA_HOST=http://172.30.96.1:11434
export PYTHONPATH=/mnt/c/Users/leer4/GH05T3/backend
export GH05T3_TEST_MODE=1
export AETHYRO_SKIP_LICENSE=1
export WSL_MODE=1
```

### Discovering WIN_HOST_IP

The Windows host IP changes when WSL restarts. To get the current value:

```bash
# Inside WSL
cat /etc/resolv.conf | grep nameserver | awk '{print $2}'
# → 172.30.96.1  (example — your IP may differ)

# Or:
ip route show | grep default | awk '{print $3}'
```

Update `~/.gh05t3-wsl.env` if the IP changes.

## Starting Services

```bash
# Inside WSL
source ~/.gh05t3-wsl.env
cd ~/gh05t3-wsl
./wsl_start.sh
```

`wsl_start.sh` starts:
- **Backend** on port 8001 (via `python backend/server.py`)
- **Gateway** on port 8002 (via `python gateway_v3.py`)

Both are started in the background with their stdout/stderr redirected to `~/gh05t3-wsl/logs/`.

### Verify services are up

```bash
# From WSL — direct port check
curl -s http://localhost:8001/health | python3 -m json.tool
curl -s http://localhost:8002/health | python3 -m json.tool

# Check Ollama reachable via Windows host
curl -s http://172.30.96.1:11434/api/tags | python3 -m json.tool
```

```powershell
# From Windows PowerShell — checking WSL-exposed ports
Invoke-RestMethod http://localhost:8001/health
Invoke-RestMethod http://localhost:8002/health
```


## Running WSL Integration Tests

### From Windows (recommended)

```powershell
# 1. Make sure WSL services are running (wsl_start.sh)
# 2. Set the flag and run
$env:WSL_SERVICES_UP = "1"
cd C:\Users\leer4\GH05T3
python -m pytest tests/test_wsl_integration.py -v
```

### From WSL

```bash
source ~/.gh05t3-wsl.env
export WSL_SERVICES_UP=1
cd /mnt/c/Users/leer4/GH05T3
python -m pytest tests/test_wsl_integration.py -v
```

### What the 6 tests check

| Test | Checks | Notes |
|---|---|---|
| `test_wsl_backend_health` | `GET /health` → 200 on port 8001 | Hard fail if down |
| `test_wsl_gateway_health` | `GET /health` → 200 on port 8002 | Hard fail if down |
| `test_wsl_gateway_agents_endpoint` | `GET /agents` → list with entries | Verifies routing |
| `test_wsl_backend_swarm_status` | `GET /swarm/status` → 200 | Ledger integration |
| `test_wsl_ollama_reachable_via_gateway` | `POST /chat` with model → not 503 | xfail on 503 (Ollama optional) |
| `test_wsl_round_trip_latency` | `/health` round trip < 500ms | Performance baseline |

### Environment variables for tests

```bash

WSL_BACKEND_URL=...     # Optional: default http://localhost:8001
WSL_GATEWAY_URL=...     # Optional: default http://localhost:8002
```

## Troubleshooting

### "Connection refused" on port 8001/8002

```bash
# Check if processes are running
ps aux | grep -E "server.py|gateway_v3"

# Check logs
tail -50 ~/gh05t3-wsl/logs/backend.log
tail -50 ~/gh05t3-wsl/logs/gateway.log

# Restart
./wsl_stop.sh && ./wsl_start.sh
```

### "Cannot connect to Ollama"

Ollama runs on Windows. From WSL, reach it at `$WIN_HOST_IP:11434`, NOT `localhost:11434`.

```bash
# Test connectivity
curl -s http://$WIN_HOST_IP:11434/api/tags

# If that fails, check Windows firewall allows WSL inbound on 11434
# Or: check that WIN_HOST_IP is still correct (it can change on WSL restart)
cat /etc/resolv.conf | grep nameserver
```

### WSL tests still skipping despite WSL_SERVICES_UP=1

Confirm the env var is set in the same shell session running pytest:

```powershell
# PowerShell — env var only lives in current session
$env:WSL_SERVICES_UP = "1"
echo $env:WSL_SERVICES_UP   # must print "1"
python -m pytest tests/test_wsl_integration.py -v
```

### ModuleNotFoundError in WSL

The venv needs `backend/` on PYTHONPATH. `~/.gh05t3-wsl.env` sets this:

```bash
source ~/.gh05t3-wsl.env
echo $PYTHONPATH   # should include /mnt/c/Users/leer4/GH05T3/backend
```

If missing, add it:
```bash
echo 'export PYTHONPATH=/mnt/c/Users/leer4/GH05T3/backend' >> ~/.gh05t3-wsl.env
```

### Port conflict with Windows stack

The WSL backend runs on the same ports (8001/8002) as the Windows stack. If you're running both simultaneously:
- Either change WSL ports: edit `wsl_start.sh` to use `--port 8011` / `--port 8012`
- Or run Windows stack first, then check if WSL tests should target Windows ports instead

## WSL Service Architecture

```
WSL Ubuntu (Linux)
├── ~/gh05t3-wsl/venv/       (Python 3.12 venv)
├── ~/gh05t3-wsl/wsl_start.sh
├── ~/gh05t3-wsl/logs/
│   ├── backend.log
│   └── gateway.log
└── ~/.gh05t3-wsl.env        (WIN_HOST_IP, OLLAMA_HOST, PYTHONPATH)

Mounts:
└── /mnt/c/Users/leer4/GH05T3/  ← same repo as Windows C:\Users\leer4\GH05T3\

Network:
├── WSL → Windows:  http://172.30.96.1:*  (Ollama, supervisor, etc.)
└── Windows → WSL:  http://localhost:8001 / :8002
    (WSL auto-forwards its ports to Windows localhost)
```

The key insight: WSL auto-forwards its listen ports to Windows `localhost`. So `curl http://localhost:8001` from PowerShell reaches the WSL backend. But WSL cannot reach `localhost:11434` for Ollama — it must use `WIN_HOST_IP`.

## SovereignCore in WSL

SovereignCore is a separate project that also runs in WSL:

```bash
# SovereignCore (separate from GH05T3 WSL services)
cd /home/leer4/sovereign-core
./scripts/start.sh   # starts on :9000
```

SovereignCore port :9000 is independent of GH05T3's :8001/:8002. Both can run simultaneously — they don't conflict. The GH05T3 supervisor at :8090 aggregates health from both.
